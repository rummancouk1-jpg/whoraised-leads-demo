## Security and failure conclusions

All 18 API route files were inspected. Activity, leads/list/edit/timeline, email/source, digest and sync require sessions; browser mutations require exact same-origin. The three cron routes check CRON_SECRET themselves; the four OHQ endpoints check OHQ_TOKEN; signup POST checks SIGNUP_WEBHOOK_SECRET. Auth POST is intentionally public but same-origin/password protected; /go GET is intentionally public. Unsupported methods do not provide a write bypass. No CORS wildcard or credential exposure was found. Proxy returns CSP nonce/strict-dynamic, HSTS, frame denial, nosniff, referrer policy and noindex; privateJson uses private,no-store. These are positive controls, not a blanket security pass: request/rate/signature/environment gaps remain above.

The Vercel CLI root probe returned HTTP 200 with the login HTML, no queue, no creator names and no David/Ian names ([root evidence](../evidence/r2-independent/preview-root.json)); direct Automation Bypass preflight returned 401 with the same login shell. Private API probes returned 401. The root discrepancy is disclosed rather than asserting all private HTML probes returned 401 or treating a login shell as an authenticated measurement.

An ordinary provider HTTP failure occurs before the stats transaction, so prior rows survive and a failing run is recorded (independent 429 replay). Stats/events replacement is one SQL transaction, but success bookkeeping is a second transaction; if that later update fails, data may have changed despite the generic “previous data is still shown” failure message (`src/lib/server/sync.ts:48`, `:51`, `:56`). A lost process can leave an unfinished run; only the recent two-minute window suppresses new work. After more than 20 consecutive failing runs the health query can lose its last-good timestamp (`src/lib/server/sync.ts:62`). These partial failure paths need isolated SQL fault tests, not production fault injection.

Observed service-worker caches contain only public static files and the offline page. No stale authenticated page/API response was served from the worker during Chromium offline navigation. A tab already holding private React state can still display its cached healthy queue when offline; that is B5. WebKit offline navigation with an active worker was not exercised because this Playwright engine crashes in that mode; only its precache and logout behavior were verified.
